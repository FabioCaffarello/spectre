# Driver handshake and conformance harness

## Context and Problem Statement

PR2 (ADR-0007) wired the protobuf schema into every consumer via
generated bindings. No component speaks the protocol over the wire
yet. PR3 closes that gap with the smallest possible end-to-end
handshake: the Playwright Node adapter starts a gRPC server on a Unix
domain socket, the Python conformance suite dials it, sends an
`InitializeRequest`, and validates the `InitializeResponse`. One RPC,
two languages, one transport.

This ADR records the implementation-level decisions PR3 forces. The
schema decisions are settled (ADR-0001, ADR-0003, ADR-0004) and the
codegen decisions are settled (ADR-0007). The remaining decisions are
about the gRPC server framework on Node, the adapter process
lifecycle, the Python conformance harness layout, and how that harness
detects driver readiness.

## Decision Drivers

- The Node adapter must speak gRPC interoperably with `grpcio` clients
  in Python. The transport choice is fixed by ADR-0003 (gRPC over UDS
  for local). The framework choice is the open question.
- The Node adapter must reuse the generated bindings produced by
  `@bufbuild/protoc-gen-es` (ADR-0007). Reintroducing a second TS
  protoc plugin or loading `.proto` at runtime would contradict that
  decision.
- Future drivers (PR4 onward, then SeleniumBase, curl-impersonate)
  will reuse the conformance harness. The harness shape established
  here must be light enough to evolve and small enough to read.
- Subprocess lifecycle has to be robust against test-failure paths.
  An assertion that throws inside a fixture cannot leak processes or
  socket files.
- The handshake test must be deterministic on developer laptops
  (Linux and macOS) and on the CI Linux runner. Windows is out of
  scope for PR3 and is documented as such.

## Considered Options

The decisions cluster into four orthogonal axes (Section 4 of the PR3
master prompt):

1. **Node gRPC framework selection.**
2. **Adapter process lifecycle and socket management.**
3. **Python conformance harness layout.**
4. **Driver readiness detection.**

Each axis is decided below with its own option set.

## Decision Outcome

### 1. Node gRPC framework

Chosen: **`@connectrpc/connect-node`** with a Node `http2` server
listening on a Unix domain socket. The server speaks the gRPC
protocol natively (not gRPC-Web, not Connect protocol) so a Python
`grpcio` client can call it without any client-side protocol shim.

Rejected:

- **`@grpc/grpc-js` with runtime `.proto` loading via
  `@grpc/proto-loader`.** The standard recommendation outside this
  project. Rejected because it bypasses the generated bindings PR2
  established as the single source of truth: `@grpc/grpc-js`
  serialises through its own `proto-loader` message classes, not
  `@bufbuild/protobuf` messages. The two type systems do not interop.
- **`@grpc/grpc-js` plus a second TS protoc plugin (e.g.
  `protoc-gen-grpc-node`).** Avoids the proto-loader mismatch but
  expands the codegen surface that ADR-0007 deliberately kept small.
  PR3 should not introduce a second TS plugin.
- **`nice-grpc` (a `@grpc/grpc-js` wrapper).** Better ergonomics than
  bare `@grpc/grpc-js`, but the same fundamental message-type
  mismatch with `@bufbuild/protobuf`.

`@connectrpc/connect-node` is the natural fit: the package consumes
`@bufbuild/protobuf` `GenService` descriptors directly (which is what
`protoc-gen-es` produces, and what already lives in
`adapters/playwright/src/proto/`), and it serves the gRPC protocol
over an HTTP/2 transport that we mount on a Node `http2` server.

The PR3 master prompt's Section 4.1 baseline ("`@grpc/grpc-js`
because we chose protocol-first in ADR-0003") was written without
the constraint that PR2 had already committed to `protoc-gen-es`.
This ADR follows ADR-0007's grain: schema generated by
`protoc-gen-es`, transport served by the `@bufbuild/protobuf`-aware
Node implementation. The transport on the wire is still gRPC.

#### `:authority` header gotcha

Node's `http2` server, when bound to a Unix domain socket, requires
the HTTP/2 `:authority` pseudo-header to be present. A bare gRPC
client that connects to `unix:/tmp/foo.sock` typically sends the
socket path or an empty value, which Node rejects.

Workaround applied in the conformance harness: the Python `grpcio`
channel is created with the channel option
`("grpc.default_authority", "localhost")`. This is the
project-canonical way to dial a UDS-bound HTTP/2 server from
`grpcio`. The harness encapsulates the workaround so individual
tests do not need to know about it. The constraint is documented in
`adapters/playwright/README.md` for any external client that wants
to call the adapter directly.

A future ADR may revisit this if a second non-Node server appears
that does not have this constraint, or if a Node release relaxes it.

### 2. Adapter lifecycle and socket management

Chosen behaviour for `adapters/playwright`:

- **Socket path resolution.** CLI flag `--socket=<absolute-path>`
  takes precedence; environment variable `SPECTRE_DRIVER_SOCKET` is
  the fallback. If neither is supplied the process exits non-zero
  with a single-line diagnostic. Both inputs accept absolute
  filesystem paths only — abstract namespace sockets and relative
  paths are rejected because macOS does not support them.
- **Stale socket cleanup.** On startup the server unlinks any file at
  the requested path. The adapter is the sole owner of its socket;
  if a previous run was killed without cleanup, the new run reclaims
  the path.
- **Readiness signalling.** A single line of the exact form
  `ready unix:<absolute-path>\n` is written to **stdout** when the
  server is accepting connections. All other diagnostic output goes
  to **stderr**. This mirrors the Language Server Protocol
  convention contributors will recognise and gives the harness a
  cheap, line-oriented signal to wait on.
- **Shutdown.** `SIGTERM` and `SIGINT` cause the server to stop
  accepting new connections, drain any in-flight RPCs, unlink the
  socket, and exit zero. A 5-second deadline applies; in-flight
  RPCs that exceed it are aborted and the process exits zero
  regardless. The harness waits up to that deadline before
  escalating.

These choices give the harness a simple lifecycle to model
(start → readiness line → RPCs → SIGTERM → exit zero) and align with
what every other driver will need to do.

### 3. Python conformance harness layout

Chosen layout under `tools/conformance/`:

```
tools/conformance/
  src/
    spectre_conformance/
      __init__.py
      harness.py        # DriverHarness class + helpers
      capabilities.py   # canonical capability-name constants
  tests/
    conftest.py         # pytest fixtures
    test_initialize.py  # the live handshake test
    test_unimplemented.py # the negative test
```

`pyproject.toml` is updated to declare the `src/` layout. The package
name `spectre_conformance` is chosen for symmetry with the existing
`spectre_seleniumbase` package and to leave room for additional
modules (planning, validators) in later PRs.

`capabilities.py` exposes capability names as string constants so
test code does not embed string literals. PR3 declares an empty
capability set; the constants module is a placeholder structure that
PR4+ will populate as RPCs come online. This converts at-least some
class of typo from a runtime AttributeError to an import-time error
once test code references named capabilities.

Rejected: a flat package at the repo root (existing layout). The
`src/` layout is chosen now while the package has a single test —
restructuring later would touch every import. The `src/` layout also
makes import errors deterministic between editable installs and
final builds.

### 4. Readiness detection

Chosen: **stdout-line primary, connect-poll fallback**, 10-second
overall timeout.

- The harness reads child stdout line-by-line on a background thread.
  When a line matches `^ready unix:.+`, the harness reports ready.
- If stdout EOFs before that line appears, or if 10 seconds pass
  with no readiness line, the harness opens a non-blocking AF_UNIX
  socket connection to the path as a last-ditch check.
- Failure surfaces a `RuntimeError` whose message includes the last
  N lines of child stderr captured to that point. A test failure is
  debuggable from the assertion message alone — the developer should
  not have to re-run with verbose flags to see the child's complaint.

The two-pronged approach costs ~10 lines of code beyond the simpler
"poll the socket" alternative. The benefit is that a misconfigured
adapter (e.g. one that crashes before listening) surfaces a real
diagnostic rather than a generic "connection refused" timeout.

### Consequences

- Good, because the chosen Node framework reuses the bindings PR2
  established and avoids reintroducing duplicate codegen.
- Good, because every future driver inherits the harness, the
  readiness-line convention, and the lifecycle contract (signal →
  drain → unlink → exit zero) as written rules rather than tribal
  knowledge.
- Good, because the negative `Navigate → UNIMPLEMENTED` test cements
  the contract that unimplemented RPCs return a structured gRPC
  status — preventing a future regression where a half-implemented
  RPC hangs or crashes the adapter.
- Bad, because the `:authority` header workaround is a footgun for
  external clients that read `driver.yaml` and try to call the
  adapter without consulting the README. Documented in two places to
  reduce the risk; will be revisited if it becomes a real friction
  point.
- Bad, because Windows support is deferred. UDS on Node + Windows is
  a known pain point and PR3's narrow scope rules it out. Future
  support is not blocked at the protocol layer (ADR-0003 explicitly
  contemplates additional transports), but it is not solved here.
- Neutral, because the harness is intentionally minimal. SeleniumBase
  and curl-impersonate will each surface real evidence about the
  shape the harness should take; PR3 does not pre-generalise.

### Confirmation

- Acceptance criteria 1–10 of the PR3 master prompt are the
  verification checklist for this ADR.
- A clean clone followed by `just bootstrap && just check` succeeds
  with no manual step on Linux and macOS.
- `just conf-test` runs the rewritten `test_initialize.py` and
  `test_unimplemented.py` against a freshly-built Playwright
  adapter, deterministically, and exits zero.
- Sending `SIGTERM` to a running adapter unlinks the socket and
  exits zero within five seconds.

## Pros and Cons of the Options

### Node gRPC framework

#### `@connectrpc/connect-node` (chosen)

- Good, because it consumes the `protoc-gen-es` `GenService`
  descriptors PR2 already generates.
- Good, because it serves Connect, gRPC, and gRPC-Web on the same
  handler, leaving room for HTTP-only clients later without changing
  the server.
- Good, because the Node ecosystem alignment is consistent: one
  package family for codegen and runtime.
- Bad, because the Node `http2` UDS `:authority` constraint surfaces
  here and must be papered over on the client side.

#### `@grpc/grpc-js` + `@grpc/proto-loader`

- Good, because it is the most widely documented choice and avoids
  the `:authority` quirk on UDS.
- Good, because the gRPC protocol is implemented by Google's
  reference Node stack, with a long deployment history.
- Bad, because the message types are `proto-loader`'s, not
  `@bufbuild/protobuf`'s. PR2's generated bindings become unused on
  the server side, which violates the spirit of ADR-0007.
- Bad, because runtime `.proto` loading reintroduces the schema as a
  runtime dependency in addition to the build-time codegen.

#### `@grpc/grpc-js` + second TS protoc plugin

- Good, because it preserves gRPC-native transport and adds typed
  service definitions.
- Bad, because two TS plugins running in lockstep is more codegen
  surface than ADR-0007 chose to maintain. The second plugin would
  need its own pinning, its own buf config, and its own tests.

### Adapter lifecycle and socket management

#### CLI flag with env var fallback (chosen)

- Good, because the engine (a future PR) can spawn drivers with
  either input depending on its launcher idioms.
- Good, because either a developer running `just pw-run` or a
  programmatic launcher reading `driver.yaml` has a working path.

#### Env var only

- Good, because it removes the precedence question.
- Bad, because manual `just pw-run` invocation becomes clunky.

#### CLI flag only

- Good, because it is the simplest contract.
- Bad, because every parent process has to construct argv just to
  pass a path.

### Readiness detection

#### Stdout-line primary, connect-poll fallback (chosen)

- Good, because misconfigured adapters surface diagnostic output in
  the assertion message instead of a generic timeout.
- Good, because the line-oriented signal is cheap to parse and
  language-agnostic.
- Neutral, because the fallback adds about ten lines of code.

#### Connect-poll only

- Good, because the harness only knows about the socket.
- Bad, because a server that fails to listen surfaces only as
  "connection refused", and the developer must re-run with
  verbose flags to find the cause.

#### Stdout-line only

- Good, because it is the cleanest contract.
- Bad, because a driver that prints the line but fails to actually
  bind would slip through.

## Update (R1.1, ADR-0020)

This ADR's decisions are partially superseded. Specifically:

- §1 (Node gRPC framework — `@connectrpc/connect-node`):
  preserved. The framework choice carries forward; only the
  transport address changes.
- §2 (Adapter lifecycle and socket management — UDS-based):
  superseded by ADR-0022 (R2). Adapters become gRPC services
  listening on TCP; service discovery replaces socket-path
  resolution; `:authority`-header workarounds and stale-socket
  cleanup become irrelevant.
- §3 (Python conformance harness layout): preserved. The harness
  shape (the `DriverHarness` class, the pytest fixture pattern,
  the `capabilities.py` constants module) stays; only the
  transport it dials changes.
- §4 (Readiness detection — stdout-line primary, connect-poll
  fallback): superseded by ADR-0022 (R2). Readiness for TCP-
  served adapter services uses gRPC health-check semantics
  rather than a stdout banner.

The refactor's phase R2 contains the implementation work that
retires the superseded portions (UDS socket creation, the
`:authority` workaround, the connect-poll fallback). See
[ADR-0020](0020-microservices-architecture-supersession.md) §5
for the full phase sequence and §4 for the chosen architectural
direction.

## Update (R2.1, ADR-0021 / ADR-0022)

Phase R2.1 ratifies the contracts the R1.1 forward reference
above sketched. The supersession of §2 and §4 is now in force;
the replacement contracts live in two companion ADRs.

- **§1 (Node gRPC framework).** Preserved unchanged. The
  `@connectrpc/connect-node` choice carries forward to the
  TCP-bound Playwright adapter; the `protoc-gen-es` /
  `@bufbuild/protobuf` alignment from PR2 stays the source of
  truth.
- **§2 (Adapter lifecycle and socket management).** Superseded
  by [ADR-0022 — TCP / gRPC transport](0022-tcp-grpc-transport.md).
  The CLI flag `--socket=`, the `SPECTRE_DRIVER_SOCKET` env var,
  the stale-socket unlink, the `:authority=localhost`
  workaround, and the SIGTERM-driven socket cleanup all retire
  in phase R2.2. Adapter bind is `0.0.0.0:<port>`; discovery is
  the env-var contract in
  [ADR-0021 — Service discovery](0021-service-discovery.md) §5.
  The full removal inventory lives in ADR-0022 §5 and
  [`docs/refactor-audit.md`](../refactor-audit.md).
- **§3 (Python conformance harness layout).** Preserved as a
  shape decision. The `src/`-layout package, the
  `DriverHarness` class name, and the `capabilities.py`
  constants module stay; what changes is the harness's
  internals — the subprocess spawn, the UDS path allocation,
  and the readiness-line parsing retire in R2.2 in favour of a
  TCP-dialling client that reads endpoints from the env-var
  contract or from a Compose service name. The pytest fixture
  pattern (one fixture per adapter) survives.
- **§4 (Readiness detection).** Superseded by ADR-0022 §3 and
  ADR-0021 §6. The stdout-line primary / connect-poll fallback
  pair retires entirely; readiness becomes the standard
  `grpc.health.v1.Health/Check` RPC, which the engine's
  startup dial (ADR-0022 §4) and the conformance harness both
  consume.

The implementation lands across PRs R2.2 (adapter transport
switch) and R2.3 (engine transport + service mode). Each PR
deletes the corresponding §2 / §4 surface in the same diff
that introduces its replacement, per the no-legacy principle
recorded in [ADR-0020](0020-microservices-architecture-supersession.md)
§4.
